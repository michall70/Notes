- **CMake**：**配置阶段**。它读取 `CMakeLists.txt`，检测系统环境、库依赖，生成供 `make` 使用的 `Makefile`（或其他构建文件）。CMake 本身不编译代码。
- **Make**：**编译阶段**。它读取 `Makefile`，调用编译器（g++/clang等）把源代码编译成目标文件，最后链接成可执行文件或库。

所以**主要编译工作确实是 `make` 完成的**，`cmake` 只是提前把编译规则翻译成 `make` 能理解的格式。

更形象的比喻：
- `cmake` 像建筑师画图纸（规划编译步骤、依赖关系）。
- `make` 像施工队（按照图纸实际干活）。

**扩展知识**：`make` 并非唯一后端。CMake 也可以生成 Ninja 文件（`-GNinja`），然后用 `ninja` 命令编译，ninja 比 make 并行效率更高。但原理相同：CMake 负责生成脚本，真正的编译由构建工具执行。

## 如何定位真正的错误

### 1. 单线程重新编译（推荐）
```bash
make clean
make -j1
```
`-j1` 让编译串行执行，错误会完整地出现在它发生的位置，不会被其他线程的警告/输出打断。

### 2. 保存完整日志并搜索 `error:`
```bash
make clean
make 2>&1 | tee build.log
grep -n -i "error:" build.log
```
`2>&1` 将标准错误也重定向到标准输出，`tee` 同时显示和保存到 `build.log`，然后搜索 `error:`。

### 3. 使用 `VERBOSE=1` 查看完整编译命令
```bash
make VERBOSE=1 -j1
```
这会显示每次编译 `g++` 的完整命令行，有助于看出是否缺少头文件路径或宏定义。

## 常见可能原因（基于 ORB-SLAM3 和 Eigen 警告）

- **Eigen 版本不兼容**：ORB-SLAM3 可能需要特定 Eigen 版本（通常 3.3.x），而你系统是 3.4+ 或包含 AVX512 相关补丁，导致 `PacketMath.h` 内代码变动，进而触发真正的编译错误（但被前面的警告遮住了）。
- **缺少头文件或定义**：例如 `Tracking.cc` 中用了 `#include <DBoW2/...>` 但路径不对。
- **C++ 标准不一致**：某些源文件需要 C++14 或 C++17，但 CMake 设置较低。
