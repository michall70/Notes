
# 一、ROS 2 是什么

ROS 2 是一套用于构建机器人应用程序的**软件库**和**工具集**，是 ROS 1 的改进和更新版本。

先说一个容易误会的点：**ROS 2 名字里虽然有 "OS"，但它不是操作系统。** 它跑在 Linux 之上，本质上是三样东西：

1. 一套**通信中间件**（底下是 DDS）
2. 一套**数据格式的约定**（消息怎么定义、话题怎么命名）
3. 一套**工具集**（命令行、可视化、录制回放）

生态方面，ROS 2 有活跃的全球开发者社区，也获得了广泛的商业硬件与平台支持。

# 二、ROS 2 解决了什么问题

## 2.1 一个机器人要干的事

我们要做一个机器人。它身上有三类东西：

- **传感器**：双目相机、激光雷达
- **执行器**：车轮、机械臂、机械足
- **数据处理器**：比如 KISS-ICP（从感知到控制）

数据要从传感器流到处理器，处理结果再从处理器流到执行器。

```
传感器  ──►  数据处理器  ──►  执行器
```

## 2.2 难点：每家硬件的接口都不一样

问题出在：**这些硬件来自不同厂商，每家的接口、API、数据格式都不一样。**


## 2.3 ROS 2 的答案：让所有人对着同一个中间件说话

ROS 2 定了一套**共同的约定**：话题怎么命名、消息怎么定义、怎么发现对方、怎么协商传输质量。

于是传感器那边写一份 ROS 2 驱动，算法那边也写一份 ROS 2 封装，**双方自动就能接上**。减少调试成本。

# 三、ROS 2 的具体实现

ROS 2 用**话题（topic）的发布 / 订阅**来传数据。

## 3.1 节点（node）

节点是 ROS 2 里**逻辑上的最小执行单元**。

一个节点可以扮演四种角色中的任意几个：**发布者（publisher）、订阅者（subscriber）、服务端、客户端** —— 也可以全都是。

> 【准确说法】通常一个进程跑一个节点，但**不是强制的**：一个进程里可以有多个节点。所以"进程 = 节点"是个方便的近似，不是定义。

## 3.3 一次"发布"，底下到底发生了什么

### 第一步：发现（discovery）—— 靠组播

节点一启动，就往一个**组播地址**喊一声："我是谁，我有哪些发布者和订阅者。"

**这个组播地址是 `239.255.0.1`。**

### 第二步：对接 —— 比对三件事

订阅方听到组播之后，会去和发布方**对比**：

1. **话题名**对不对得上
2. **消息类型**一不一样（点是float32类型还是float16）
3. **QoS 兼不兼容**

三样都通过，双方才建立点对点连接。

#### QoS（服务质量）

QoS 是 DDS 提供的一组"传输质量"开关。ROS 2 暴露出来的主要有这几条：

| 策略                  | 取值                             | 意思是                 |
| ------------------- | ------------------------------ | ------------------- |
| **Reliability** 可靠性 | `RELIABLE` / `BEST_EFFORT`     | 丢包要不要重传             |
| **Durability** 持久性  | `VOLATILE` / `TRANSIENT_LOCAL` | 后连上来的订阅者，要不要补发历史消息  |
| **History** 历史      | `KEEP_LAST` / `KEEP_ALL`       | 缓存最后 N 条，还是全留       |
| **Depth** 深度        | 整数                             | 配合 `KEEP_LAST`，缓存几条 |
| **Deadline** 截止时间   | 时长                             | 期望对方多久至少来一条         |
| **Lifespan** 寿命     | 时长                             | 一条消息多久算过期           |
| **Liveliness** 活跃性  | `AUTOMATIC` / `MANUAL`         | 怎么判断对方还活着           |

>⚠️ 最有意思的一条规则：订阅方的要求，不能超过发布方的能力

如果发布方用的是最省事的 `BEST_EFFORT`（**允许丢包**），而订阅方却要求 `RELIABLE`（**必须不丢**）——

**双方会静默地接不上。** 一条数据都收不到，只在日志里留一行警告：

```
[WARN] New subscription discovered on topic '/xxx', requesting incompatible QoS.
       No messages will be sent to it. Last incompatible policy: RELIABILITY_QOS_POLICY
```

> 【这条我做过实验】同一个话题，发布方 `BEST_EFFORT`：
> - 订阅方要 `RELIABLE` → **收 0 条**，日志里出现 `requesting incompatible QoS`
> - 订阅方用 `BEST_EFFORT` → **收 39 条**，正常
>
> **它不报错，不崩溃，就是不给你。** 这种坑不知道规则的话能查一整天。

**道理其实很直白：订阅方不能要求发布方许诺它做不到的事。**


### 第三步：传数据 —— 改成单播

**发现用组播，数据用单播。** 因为组播要发给所有人在听的人，效率低；一旦对接上了，就点对点发。

## 3.5 四种通信机制，怎么选

| 机制               | 模式            | 适合什么      | 例子        |
| ---------------- | ------------- | --------- | --------- |
| **话题 topic**     | 发布 / 订阅，单向，持续 | **高频数据流** | 点云、图像、IMU |
| **服务 service**   | 请求 / 响应，一问一答  | 要一个即时结果   | 查询电池电量    |
| **动作 action**    | 长任务，可中途反馈、可取消 | 耗时又要知道进度  | "走到那个点去"  |
| **参数 parameter** | 配置项，可读可改      | 调参        | 最大速度      |

**关键区别：传感器数据必须走话题，不能走服务。**

因为传感器是**一直在往外发**的（10 Hz、30 Hz），而服务是"你问一次、我答一次"——**你不可能用"问一次答一次"去接一个每秒发 30 帧的相机。**

# 四、举例


拿激光雷达 SLAM 举例：

1. 激光雷达实时采集点云，把每一帧发布到 `/lidar` 这个话题上
2. KISS-ICP 订阅 `/lidar`，拿到点云做帧间配准，估计出每帧的位姿，把点云拼成一张全局地图

**这个过程最关键的一点是：点云不需要落地成文件。**

不是"雷达存一帧到磁盘、算法再从磁盘读"——**是雷达进程直接把内存里的点云交给了算法进程。**

双方要谈拢的只有三件事：

| 要谈拢的     | 例子                                                         |
| -------- | ---------------------------------------------------------- |
| **话题名**  | 是 `/lidar` 还是 `/utlidar/cloud`                             |
| **消息类型** | 是 `sensor_msgs/msg/PointCloud2` 还是 `sensor_msgs/msg/Image` |
| **QoS**  | 可靠传输，还是尽力而为                                                |

对上就能通信。**双方不需要知道对方的代码长什么样，甚至不需要知道对方跑在哪台机器上。**

ROS 2 已经把主要框架搭好了，有完善的工具库和社区贡献的功能包。

**我们只需要调用它提供的 API，就能搭自己的应用。**
